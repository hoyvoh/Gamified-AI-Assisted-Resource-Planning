### Circular FK Resolution

Two circular references exist in the schema. Both are handled by making one side nullable
and deferring the FK population until after both rows exist:

| Circle | Resolution |
|--------|-----------|
| `projects.active_scenario_id → scenarios.id` | Both nullable; set after scenario is created |
| `projects.evaluation_id → project_evaluations.id` | Both nullable; set after evaluation is created |

In the Alembic migration, these circular FKs are added via `batch_alter_table` after both
tables are created, rather than inline with the `CREATE TABLE` statement.

## Configuration Strategy

### Enum Values

All `ENUM` columns are declared with `native_enum=False`. This means:
- SQLite: stored as VARCHAR (works without DDL `CREATE TYPE`)
- PostgreSQL (future): also VARCHAR with check constraint — no separate migration step needed

Named constants for valid enum values live at module level in each model file (e.g.
`TASK_STATUS_VALUES`, `SENIORITY_VALUES`). This avoids magic strings in application code.

### JSONB vs JSON

All JSONB columns in the spec are declared as `JSON` in the ORM models. SQLAlchemy maps
`JSON` to native `JSONB` in PostgreSQL and to `TEXT` with JSON serialization in SQLite.
No application code changes when switching databases.

### `effort_total_days` — App-Managed Column

The spec marks `tasks.effort_total_days` as `GENERATED` (sum of the six phase columns).
SQLite does not support generated columns. This column is declared as a plain `DECIMAL(6,2)`
and is managed by the application layer — it must be recomputed and saved whenever any
phase effort column changes.

### UUID Primary Keys

All PKs use `sa.Uuid(as_uuid=True)` (SQLAlchemy 2.0 type). SQLite stores UUIDs as
16-byte binary. Application code always works with Python `uuid.UUID` objects.
