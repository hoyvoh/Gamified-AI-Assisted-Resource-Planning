# ISO/IEC 25010: Software Quality Model

## Overview

ISO/IEC 25010 is the international standard defining a **hierarchical quality model** for software systems. It provides a structured vocabulary for specifying quality requirements and evaluating whether systems meet those requirements.

Its primary value in our system:
> **It is the "quality attribute dictionary" used by ATAM to define what dimensions of quality matter.**

Without a shared vocabulary for quality, architecture evaluations become inconsistent ("secure" means different things to different stakeholders). ISO 25010 resolves this.

---

## The Two Quality Models in ISO 25010

### Model 1: Product Quality Model (8 characteristics)

The **Product Quality Model** describes intrinsic quality of the software itself. It is the primary model for architecture and design evaluation.

### Model 2: Quality in Use Model (5 characteristics)

The **Quality in Use Model** describes quality as experienced by users in a real operational context. It is used for post-deployment evaluation and acceptance testing.

---

## Model 1: Product Quality — 8 Characteristics

### 1. Functional Suitability

*Does the software provide all required functions correctly?*

| Sub-characteristic | Definition |
|-------------------|------------|
| **Functional Completeness** | All specified functions are implemented |
| **Functional Correctness** | Functions produce accurate results |
| **Functional Appropriateness** | Functions are fit for purpose (appropriate to goals) |

**Project evaluation use:** Validate that the proposed project scope is complete and well-specified before development begins. A project with ill-defined functional requirements will fail this dimension.

---

### 2. Performance Efficiency

*Does the software use resources appropriately relative to stated conditions?*

| Sub-characteristic | Definition | Typical metric |
|-------------------|------------|---------------|
| **Time behaviour** | Response and processing times | p50/p95/p99 latency; throughput |
| **Resource utilisation** | CPU, memory, disk, network usage | % utilization at target load |
| **Capacity** | Maximum operational limits | Max concurrent users; max data volume |

**Project evaluation use:** Projects must specify non-functional performance requirements. A project without defined SLAs cannot be evaluated for performance feasibility.

**Key question for assessment:** *Has the team specified target performance under realistic load conditions?*

---

### 3. Compatibility

*Can the software work alongside or exchange information with other systems?*

| Sub-characteristic | Definition |
|-------------------|------------|
| **Co-existence** | Operates in shared environment without degrading others |
| **Interoperability** | Exchanges information with other systems correctly |

**Project evaluation use:** Critical for integration projects. Interoperability is a common ATAM risk area when projects depend on external APIs, data formats, or protocols.

---

### 4. Usability

*Can users achieve their goals effectively and efficiently with acceptable satisfaction?*

| Sub-characteristic | Definition |
|-------------------|------------|
| **Appropriateness recognisability** | Users can tell if the software fits their needs |
| **Learnability** | Users can learn to use it without excessive effort |
| **Operability** | Easy to operate and control |
| **User error protection** | Prevents and handles user errors gracefully |
| **User interface aesthetics** | Visually and interaction-design quality |
| **Accessibility** | Usable by people with disabilities |

**Project evaluation use:** Often underspecified in project briefs. Evaluate whether the project has a user research foundation or UX design plan.

---

### 5. Reliability

*Does the software maintain its performance level under stated conditions for a stated time period?*

| Sub-characteristic | Definition | Typical metric |
|-------------------|------------|---------------|
| **Maturity** | Avoidance of failures under normal conditions | MTBF (Mean Time Between Failures) |
| **Availability** | System operational and accessible when needed | Uptime % (e.g., 99.9% = 8.7 hrs/yr downtime) |
| **Fault tolerance** | Operates despite hardware/software failures | Graceful degradation behavior |
| **Recoverability** | Can restore operation after failure | MTTR (Mean Time to Recovery) |

**Project evaluation use:** Projects serving business-critical functions must specify availability SLAs. A project without reliability requirements has an implicit assumption of "reliability doesn't matter" — which is rarely true.

**SLA reference table:**

| Availability | Max annual downtime | Common use |
|-------------|--------------------|-----------|
| 99% | 87.6 hours | Internal tools |
| 99.9% | 8.7 hours | Business apps |
| 99.95% | 4.4 hours | Customer-facing |
| 99.99% | 52 minutes | Mission-critical |
| 99.999% | 5 minutes | Financial systems |

---

### 6. Security

*Does the software protect information and data from unauthorized access?*

| Sub-characteristic | Definition |
|-------------------|------------|
| **Confidentiality** | Data accessible only to authorized parties |
| **Integrity** | Data and system state protected from unauthorized modification |
| **Non-repudiation** | Actions can be proven to have occurred |
| **Accountability** | Actions of an entity can be traced to that entity |
| **Authenticity** | Identity of subjects and resources can be verified |

**Project evaluation use:** Security requirements must be explicit. Projects handling personal data (GDPR), financial data (PCI-DSS), or health data (HIPAA) have legally mandated security requirements. The absence of a security specification is a TELOS Legal risk.

**Security assessment questions:**
1. What data does this system store or transmit?
2. Who should and should not have access?
3. What happens if data is compromised?
4. Is a threat model (e.g., STRIDE) planned?

---

### 7. Maintainability

*How effectively can the software be modified by intended maintainers?*

| Sub-characteristic | Definition | GitHub signal |
|-------------------|------------|--------------|
| **Modularity** | System composed of discrete components | PR scope, file touch patterns |
| **Reusability** | Components can be used in multiple systems | Library/shared module usage |
| **Analysability** | Ease of diagnosing defects or changes | Log quality, tracing, error messages |
| **Modifiability** | Can be changed without introducing defects | Code complexity, coupling metrics |
| **Testability** | Ease of verifying behavior via tests | Test coverage, test structure |

**Project evaluation use:** Maintainability is the most frequently underspecified dimension. A project that ships fast but accumulates technical debt trades short-term velocity for long-term maintainability. The architecture review should assess whether the proposed design makes future change easy or hard.

---

### 8. Portability

*Can the software be moved to different environments?*

| Sub-characteristic | Definition |
|-------------------|------------|
| **Adaptability** | Can be adapted to different environments |
| **Installability** | Can be installed in specified environments |
| **Replaceability** | Can replace other software for same purpose |

**Project evaluation use:** Relevant when: (a) multi-cloud or cloud-agnostic requirements exist, (b) on-premises deployment is required alongside cloud, (c) the software must migrate between vendors.

---

## Model 2: Quality in Use — 5 Characteristics

| Characteristic | Definition |
|----------------|------------|
| **Effectiveness** | Users achieve goals with accuracy and completeness |
| **Efficiency** | Resources expended relative to effectiveness achieved |
| **Satisfaction** | User needs are satisfied (usefulness, trust, pleasure, comfort) |
| **Freedom from risk** | Risk to economic status, human life, health, environment is mitigated |
| **Context coverage** | Used effectively across relevant usage contexts |

## Applying ISO 25010 to Project Evaluation

### Quality Attribute Prioritization Exercise

For each project, stakeholders should explicitly rank the 8 product quality characteristics by importance **for this specific project**. Different projects have fundamentally different priority profiles:

| Project type | Primary quality priorities | Secondary | Often de-prioritized |
|-------------|--------------------------|-----------|---------------------|
| Consumer mobile app | Usability, Performance | Reliability | Portability |
| Financial system | Security, Reliability, Accuracy | Performance | Usability |
| Internal tooling | Usability, Maintainability | Performance | Portability |
| Data pipeline | Performance, Reliability | Maintainability | Usability |
| Healthcare software | Security, Reliability | Usability | Performance |
| Open source library | Maintainability, Portability | Testability | Usability |

### Quality Profile Scoring (per axis, 1–5)

For the project analysis radar, each ISO 25010 dimension is scored based on **how well the project brief and architecture address it**:

| Score | Criteria |
|-------|----------|
| 1 | No requirements specified for this dimension; architecture ignores it |
| 2 | Dimension acknowledged but no specific requirements or design decisions |
| 3 | Basic requirements specified; some architectural consideration |
| 4 | Clear requirements with measurable targets; architectural decisions explicitly support |
| 5 | Full SLA/NFR specification; architectural patterns explicitly chosen for this dimension; test/validation plan |

### Quality Gaps as ATAM Risks

Any quality dimension that scores ≤ 2 that is **high priority for this project type** is automatically an ATAM risk:

```
if quality_score[dimension] ≤ 2 AND priority[dimension] == HIGH:
    → Register as architectural risk
    → Require mitigation plan before proceeding
```

## ISO 25010 vs. Other Quality Frameworks

| Framework | Scope | Relationship to ISO 25010 |
|-----------|-------|--------------------------|
| **ATAM** | Architecture evaluation | Uses ISO 25010 as quality attribute vocabulary |
| **DORA** | DevOps performance | Maps to Performance, Reliability, Maintainability |
| **SPACE** | Developer productivity | Maps to Efficiency, Satisfaction (Quality in Use) |
| **SonarQube rules** | Code quality | Maps primarily to Maintainability, Reliability, Security |
| **WCAG 2.1** | Accessibility | Sub-set of Usability (Accessibility sub-characteristic) |
| **OWASP Top 10** | Security vulnerabilities | Sub-set of Security characteristic |
